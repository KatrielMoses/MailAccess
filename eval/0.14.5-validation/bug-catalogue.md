# MailAccess 0.14.5 — Bug Catalogue (severity-ranked)

## Environment (not a product bug, but was masking the true baseline)
- **ENV-1 (High, local-only, but contaminated a committed artifact):** `%LOCALAPPDATA%\Temp\pytest-of-Katriel Delzyn Moses` is ACL-locked (WinError 5, access denied even to list/remove). Any pytest using the `tmp_path` fixture errors at *fixture setup*. Impact was far larger than first thought: with the broken temp dir the gate snapshot recorded **292** failing nodeids; with a clean `TEMP` it records **74**. i.e. ~**218** of the "failures" were this one env fault. The previously-committed baseline (279) was captured under the same fault, so **it too was contaminated** — the honest known-failure count under a healthy environment is ~74. **Workaround (used for all snapshots/tests here):** export `TEMP`/`TMP` to a clean dir. **Owner fix:** delete/reset ACLs on that dir from an elevated shell. **Harness hardening (recommended):** `eval/harness/pytest_baseline.py` should pass a fixed `--basetemp` (or set TMPDIR) so the gate is robust to the machine's temp-dir ACLs and baseline/check stay like-for-like. Not a product defect.

## Product / test findings (from gate baseline triage)
- **BUG-1 (Medium, correctness invariant):** `apollo` and `pdl` were added to `SOURCE_WEIGHTS` (Phase 7A/7B, email_confidence.py:40-41) but NOT to `SOURCE_CLASS` (email_confidence.py:128). Violates the invariant `set(SOURCE_WEIGHTS) <= set(SOURCE_CLASS)` (test_confidence_model_phase2::test_source_class_mapping_complete, red). `source_class_of()` silently falls back to returning the source_type string as its own class, so apollo/pdl claims are not grouped into a source *family* for calibration per-source-FP accounting. Live impact low (enrichment is BYO-key, inert without keys) but it's a real wiring gap. **Fix:** add `"apollo": "api", "pdl": "api"` (or a new "enrichment" family) to SOURCE_CLASS. Trivial, unambiguous.

- **BUG-2 (Low, stale test):** `test_aggressive_mode_wiring::test_aggressive_passes_true_to_dork` (new in phase work) asserts email_search_dork.run is called in an aggressive mock harvest, but Phase 5B's cc-first posture (default `cc_first=True`) reschedules the live-search dork onto a best-effort track that isn't invoked in the mock scenario. Confirmed: passes with `CC_FIRST=false`. Behavior is intended (5B). **Fix:** update the test to set cc_first=False or assert cc-first-aware scheduling.

- **BUG-3 (Low, stale test):** `test_orchestrator_budget_integration::test_slow_module_gets_partial_result` (new) asserts the slow module `commoncrawl_email` is recorded via the patched `_run_module`; under cc-first (default) commoncrawl runs via the guaranteed-track path, so the white-box monkeypatch isn't hit. The behavioral guarantee (no crash; valid DomainHarvestResult) still holds. Confirmed: passes with `CC_FIRST=false`. **Fix:** update the test's intercept/assumption for the cc-first path.

- **BUG-4 (Medium, live-path gap — the flagged Phase-6 outstanding item):** 4A calibration capture does **not accrue on a real CLI harvest**. After a cold live harvest of lavellenetworks.com (4 leads, all graded with `deliverability_score`+`grade` in the export), the run's DB has `score_feature_snapshots = 0`. The machinery is sound — `capture_batch` is wired into the live path (`run_domain_harvest`→`run_adaptive_harvest`→`_grade_leads_and_capture`→`_apply_deliverability_grade`→`capture_batch` at domain_harvest_orchestrator.py:1290) and writes correctly when called standalone against the same DB with the real feature dict (both `known_outcome=None` and `"verified"` paths OK). But in the live harvest the `capture_batch` call is wrapped in a `try/except` that swallows to `logger.debug` (orchestrator:1291-1292; scoring_capture.py:243-245 also swallows to `logger.debug("scoring capture batch skipped")`), so the failure is silent. Net effect: 3D grades populate (✅) but 4A feature snapshots never accrue in production → the promotion gate can never gather real labels. **Root cause (found): SAME as BUG-5 — the cold-DB init race.** On the in-process harvest, `_apply_deliverability_grade` first calls `corpus_store.read_verification_history` (a 3C signal read) and then, per lead, builds `capture_records` and calls `capture_batch`. On a cold DB the schema wasn't migrated yet, so the surrounding corpus reads failed and the `score_feature_snapshots` write silently no-oped (0 rows) even though grading set the export fields. **FIXED (2026-09-07) by the BUG-5 fix:** `_ensure_schema()` now runs at the top of `read_verification_history` (called at the very start of the grading pass), so the full schema exists before grading + capture. **Verified live:** a fresh cold harvest now records `capture_records=4 → capture_batch wrote=4`, `score_feature_snapshots = 4` (was 0). Regression covered by `tests/test_corpus_store.py::test_cold_db_read_first_ensures_schema_no_error`.
- **Impact / was non-blocking:** 4A capture feeds only the deferred calibration promotion gate (shadow-only; live scoring stays hand-tuned), so this never affected 0.14.5 live output — but the flywheel now accrues labels correctly.

- **BUG-5 (Low/Medium, cold-harvest DB-init race):** On a COLD harvest against a brand-new DB, the corpus **read-first** (Phase 1D) runs before Alembic migrations finish, so `corpus_store.read_fresh_crawl` (corpus_store.py:94) throws `sqlite3.OperationalError: no such table: crawl_snapshots` (also `verification_outcomes`, 2×). Logged as "Corpus read-first failed for <domain>; will collect fresh" and recovered — the harvest collects fresh and writes the crawl_snapshot back at the end (alembic_version ends at 0009, crawl_snapshots=1). **So: no yield/parity impact, but the first cold read-first optimization is skipped and stack traces are logged.** The server-backed investigate path does not hit this (its lifespan startup awaits `init_db()` before any query). Warm re-harvests work perfectly (proven: 114s→2s, ~57×, "+0/-0/4 unchanged").
  **FIXED (2026-09-07):** added a process-level `_ensure_schema()` guard in `backend/core/corpus_store.py` (runs `init_db()` once per process) and call it at the top of `read_fresh_crawl` (the read-first path) and `read_verification_history` (the per-lead 3C signal read that can be reached even when read-first is skipped via `--force`). `init_db()` runs Alembic on every call, so the once-per-process flag avoids per-lead migration cost. **Verified:** fresh cold harvest now logs **0** "no such table" errors and **0** "Corpus read-first failed", yield preserved (4 emails).
