# Phase 1A — Schema-versioning foundation (Alembic)

Replaces the hand-rolled startup migration path in `backend/db/database.py`
(the `create_all` + a sequence of idempotent `ALTER TABLE … ADD COLUMN`
inspector checks) with real, versioned, reversible Alembic migrations — applied
automatically at startup, non-breaking, and reversible. SQLite remains the
default; Postgres is made correct when configured.

## What changed

| Before | After |
|---|---|
| `init_db` → `create_all` + 7 `_migrate_add_*` idempotent ALTER helpers | `init_db` → apply Alembic migrations to `head` |
| No version history, no down-migrations | `alembic_version` table; two revisions with real `downgrade()` |
| `.env.example` advertised a **sync** `postgresql://` URL (fails on the async engine) | `.env.example` documents the required **async** `postgresql+asyncpg://` URL |

No schema *content* changed: `head` is byte-for-column identical to v0.14.4. No
new tables or columns were added — those land in Phases 1C/1D.

## Design decisions (exploration latitude)

### Config layout
- `alembic.ini` at the repo root — for **standalone** `alembic` CLI use only
  (`alembic history` / `upgrade` / `downgrade` during development and in the
  migration tests). `sqlalchemy.url` is left blank; `env.py` falls back to the
  app's `settings.database_url`, so the CLI and the app target the same DB.
- The migration environment lives at `backend/db/migrations/` (`env.py`,
  `script.py.mako`, `versions/`), colocated with the models and packaged into
  the wheel by hatchling automatically (verified).
- At **startup**, `init_db` does *not* read `alembic.ini`. It builds a `Config`
  programmatically with an absolute `script_location`, so migrations apply
  correctly even under the isolated working directories that investigate/harvest
  runs use.

### How the async engine reaches Alembic
`env.py` is **dual-mode**:
- **Embedded (startup):** `init_db` opens `engine.begin()` and, inside
  `run_sync`, hands the resulting *sync* Connection to Alembic via
  `config.attributes["connection"]`. Migrations run on the app's own async
  engine — no second engine, and no nested event loop — so it works for both
  `aiosqlite` and `asyncpg` without adding a separate sync driver.
  `engine.begin()` (not `connect()`) is required: `init_db` introspects the
  connection to decide whether to stamp a pre-Alembic DB, which autobegins a
  transaction in SQLAlchemy 2.0; `begin()` owns and commits that transaction so
  Alembic's DDL and version writes are durable.
- **Standalone (CLI):** with no pre-supplied connection, `env.py` builds its own
  async engine and drives it with `run_sync`.

### Baseline captured as **two hand-written** revisions
- `0001_baseline` — the core `investigations` / `module_runs` / `findings`
  tables as they existed *before* the ALTER sequence.
- `0002_enrichment_columns` — the eleven `investigations` columns the
  `_migrate_add_*` helpers used to add on every startup (graph_data,
  credential_risk_score, canonical_email, timeline_json, defenders_brief_json,
  the name-consensus fields, and the started_at/error recovery fields), plus the
  `canonical_email` index.

Why hand-written and split, rather than a single autogenerated baseline:
- The old ALTERs *are* an unversioned incremental history; expressing them as
  `0001 → 0002` is faithful to that history and yields a **real, meaningful
  down-migration** to test (drop exactly those eleven columns + the index), as
  the brief requires.
- The enum type and every column type were transcribed against the *ground
  truth* dumped from `Base.metadata.create_all` on SQLite (status → `VARCHAR(8)`
  storing the uppercase member names; a native `investigationstatus` enum on
  Postgres, dropped on `0001` downgrade). A test asserts fresh-via-Alembic is
  schema-equivalent to `create_all`.

`target_metadata = Base.metadata` is wired in `env.py` so `alembic revision
--autogenerate` works for the new tables in later phases.

### Stamp-and-reconcile for a heterogeneous install base
Real pre-Alembic databases are **not uniform**:
- one freshly created by v0.14.4 `create_all` has every column *and* the
  `canonical_email` index;
- one upgraded across versions via the old `ADD COLUMN` path has the columns but
  is **missing** `ix_investigations_canonical_email` (the old ALTER never
  created it), and may carry an orphaned legacy `domain_discoveries` table.

`init_db` handles all of them: if `investigations` exists but `alembic_version`
does not, it **stamps the DB at `0001`** (so `0001`'s `create_table` is skipped)
and then upgrades. `0002` is written to be **guarded/idempotent** — every column
and the index are added only if absent, via live introspection — so it
reconciles each of those states forward to the identical `head` schema,
including restoring the missing index. Orphan tables outside `Base.metadata`
(e.g. `domain_discoveries`) are never referenced and are left untouched.

Physical column *order* still differs between a fresh Alembic DB (core columns,
then enrichment appended) and a `create_all` DB (model order) — exactly as it
already differed between a fresh and an upgraded v0.14.4 DB. Order is not part of
the logical schema; the equivalence check is column-set / types / nullability /
indexes.

### `_clean_stale_investigations` — multi-process caveat noted, not solved
Behavior is preserved. A comment records the constraint: under a future
multi-process deployment two workers could both run the startup sweep; the
`UPDATE` is idempotent (only flips `RUNNING → FAILED` past the 10-minute cutoff)
so a double run is harmless, but it does not guard a healthy long-running
investigation owned by another live worker. An owner/heartbeat mechanism is
deferred, per the brief.

## Downgrade path (documented + tested)

`0002 → 0001` is a real round-trip. Column drops use Alembic **batch mode**
(table-recreate) so they work on SQLite < 3.35 (which lacks native `DROP
COLUMN`) as well as Postgres.

Tested two ways:
- `tests/test_alembic_migrations.py::test_downgrade_round_trip` — upgrade `head`
  → downgrade `0001` (asserts exactly the eleven enrichment columns + the index
  are gone, core intact) → upgrade `head` (asserts full reversibility).
- Standalone CLI (throwaway DB):
  ```bash
  DATABASE_URL="sqlite+aiosqlite:///$(mktemp -d)/cli.db" alembic upgrade head
  DATABASE_URL="sqlite+aiosqlite:///$(mktemp -d)/cli.db" alembic downgrade -1
  ```

> The standalone CLI does not perform the startup stamp-detection, so a raw
> `alembic upgrade head` should target a fresh DB or one already initialized by
> the app. In normal operation users never invoke `alembic` directly — `init_db`
> applies and reconciles migrations on every startup.
