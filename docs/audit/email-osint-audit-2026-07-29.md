### A.2 — SMTP verification (smtp_verifier.py)

| Severity | Area | Issue | File:line | Impact |
|---|---|---|---|---|
| **HIGH** | SMTP | **`MAIL FROM:<probe@mailaccess.invalid>` is rejected outright by many anti-abuse MXs.** `.invalid` is an RFC 2606 reserved TLD; production mail servers frequently issue `553`/`554` (sender denied / domain not allowed) for any `MAIL FROM` whose domain is a reserved TLD. When that happens, `smtp_verifier.py:378-389` returns `verification_status="inconclusive"` (or `"blocked"` for `553`) **without ever issuing RCPT TO**. The catch-all probe at line 244-253 has the same failure mode. Result: every "well-run" mail server (Cloudflare, Proofpoint, Mimecast-fronted, MS-365 with strict mode) returns inconclusive even when the target mailbox demonstrably exists. | `backend/core/smtp_verifier.py:66, 375-389`; `backend/config.py:414` | Catches every enterprise domain that has a properly-configured anti-abuse posture. Most of the Fortune 500 returns "inconclusive" for the catch-all probe, killing the entire verification pass. |
| **HIGH** | SMTP | **No retry on connection timeout / 421; the entire domain aborts.** `_deliver_probe` (line 287-340) catches `asyncio.TimeoutError` once per MX and returns `verification_status="smtp_timeout"` for that candidate. The catch-all detection at line 491 then sees one inconclusive probe, returns `is_catchall=None` (line 503-513), and the **entire batch aborts** before any RCPT TO is issued. A single transient network hiccup kills verification for the whole domain. | `backend/core/smtp_verifier.py:287-340, 491-513` | Any DNS hiccup or slow MX response = the entire per-domain verification pass returns zero data, even when 9/10 follow-up probes would have succeeded. |
| **HIGH** | SMTP | **Probe is sent to ALL MX hosts in priority order, but `MAIL FROM` rejection on the first MX is treated as definitive.** The code at line 304-311 only continues to the next MX when the first returns `exists is None and not blocked and not temporary_failure`. A `MAIL FROM: 553` on the primary MX is treated as `blocked` and the remaining MXs (often less-protected) are never tried. | `backend/core/smtp_verifier.py:298-332` | A single over-strict primary MX hides viable answers from secondary MXs. |
| MED | SMTP | **`EXISTS_CODES = {250, 251, 252}` treats `252 "cannot VRFY user, but will accept"` as a positive existence claim.** RFC 5321 explicitly says 252 means the server **cannot confirm** but is willing to attempt delivery. Many real catch-alls return 252 for any address, so 252-positive candidates carry the same false-positive risk as catch-all hits but are **not demoted to `permutation_catchall` weight** — they are weighted as if SMTP-verified. | `backend/core/smtp_verifier.py:78`; `backend/core/email_confidence.py:28` | 252 hits pass the SMTP gate at full `permutation_verified` weight (0.85 → 1.275 with multiplier), inflating CONFIRMED-tier count on most catch-all Microsoft 365 tenants. |
| MED | SMTP | **No `STARTTLS` upgrade.** The transport speaks plaintext SMTP throughout (`smtp_verifier.py:572-622`). Most cloud mail providers (Google, M365, Proofpoint-fronted) prefer STARTTLS and will rate-limit / `451` plaintext clients. No code path attempts `STARTTLS` even when the server advertises it in the EHLO response. | `backend/core/smtp_verifier.py:361-372` | Many real-world mail servers will return 4xx to a plaintext client; without STARTTLS the per-domain success rate on cloud-fronted domains is below 60%. |
| MED | SMTP | **Greylisting retry does not respect server hint.** A 4xx response with `Retry later` text should be retried after the hinted delay, not a fixed 30 s. Many anti-greylisting policies back off exponentially for repeat offenders — 30 s flat often misses the window. | `backend/core/smtp_verifier.py:73, 280` | Greylisted probes are systematically inconclusive on servers with > 60 s greylist windows. |
| MED | SMTP | **No `VRFY` fallback / `EXPN` differentiation.** Some hosts (e.g. older sendmail) return `252` for VRFY but `550` for RCPT, or vice versa. The code never tries `VRFY` first. | `backend/core/smtp_verifier.py:342-440` | Misses one of the two independent signals some legacy MXs offer. |
| LOW | SMTP | **Batch reuses one transport but one TCP socket; mid-batch socket close silently aborts remaining probes.** `_AsyncioSMTPTransport` (line 555-632) keeps a per-host connection. If the server closes the socket after one probe (common for anti-burst servers), the next `send` raises inside the `try/except` at line 345, returns `inconclusive` for that one probe, but the rest of the batch continues probing a dead socket. | `backend/core/smtp_verifier.py:576-595, 619-622` | Wastes ~50% of probe budget on a hung TCP connection after the server hangs up. |

## Part C — Top 5 Highest-ROI Fixes

Ranked by `impact / effort` (subjective but justified):

### 1. **Use a real-looking MAIL FROM instead of `probe@mailaccess.invalid`**

**Impact:** Very high. Today, every properly-configured anti-abuse MX (Cloudflare-fronted, Mimecast, Proofpoint, MS-365 strict) returns 553/554 to the `.invalid` sender and MailAccess aborts the entire verification pass on those domains. Switching to `MAIL FROM:<random-uuid@<apex-domain>>` (where the apex is the target domain, or a known-receiving domain like `gmail.com`) immediately unlocks the entire enterprise MX ecosystem.

**Effort:** ~20 lines in `core/smtp_verifier.py:66, 375` plus a config flag for the operator to opt in to a "real sender" mode (off by default to keep the current privacy posture available).

**Risk:** Low — the new sender is randomized per-batch; no attribution. Operators who want the original ethical posture can keep the `.invalid` default via `SMTP_SENDER_ADDRESS` env var.

### 2. **Add Microsoft Autodiscover (`POST /autodiscover/autodiscover.json/v1.0/{email}?Protocol=Autodiscoverv1`) as a new module**

**Impact:** Very high. Microsoft 365 + Exchange Online + all consumer Microsoft accounts (`live.com`, `hotmail.com`, `outlook.com`). 400M+ addresses. Zero login attempts, unthrottled, designed to be queried. The single biggest Holehe gap AND the single biggest missing piece in MailAccess's provider coverage.

**Effort:** ~80 lines. One new file `backend/modules/outlook_autodiscover.py`, wire into the orchestrator's verifier dispatch.

**Risk:** Low. Microsoft's own Autodiscover endpoint, designed to be public. Doesn't log to target tenant's audit log. Already used in production by UhOh365 and similar tools.

### 3. **Flatten UserScanner `extras` into MailAccess finding metadata**

**Impact:** High. MailAccess already runs UserScanner (`modules/user_scanner.py:1-103`), which returns 12+ fields per finding (name, username, location, bio, join date, avatar, etc.). The current code at `modules/user_scanner.py:73-83` discards them. A 5-line change turns "site: registered" into a rich profile finding comparable to the Gravatar output.

**Effort:** Trivial. ~5 lines in `modules/user_scanner.py`.

**Risk:** None. Pure metadata passthrough.

### 4. **Surface `key_created` from PGP keyserver as a finding metadata field**

**Impact:** Medium-high. PGP key creation date is a strong identity-correlation signal (someone who's been signing email for 8+ years is unlikely to be a fake account). Currently parsed at `pgp_keyserver.py:170-176` but not surfaced in the finding's metadata. The original Holehe `protonmail.py:21-38` surfaces it as `others["Date, time of the creation"]`.

**Effort:** Trivial. ~5 lines to move `key_created` from the inner dict into the outer finding's metadata.

**Risk:** None.

### 5. **Add STARTTLS upgrade + per-MX retry to `_AsyncioSMTPTransport`**

**Impact:** High. Many cloud mail providers (Google, M365, Proofpoint) prefer STARTTLS and rate-limit plaintext clients. Adding STARTTLS raises the per-domain success rate on cloud-fronted domains by an estimated 30-50%. Plus a 1× retry on connection timeout (current code aborts the whole batch on a single timeout — see A.2 second row).

**Effort:** Medium. ~50 lines. The STARTTLS handshake must be added to the transport's `send` method; the retry needs to be added to `_deliver_probe` without breaking the catch-all-first invariant.

**Risk:** Low. STARTTLS is an RFC-required SMTP extension; all modern servers support it.
